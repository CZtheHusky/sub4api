## 结论含义

- **建议引入**：当前存在缺口，代码改动具有直接价值；不表示已验证可以无冲突 cherry-pick。
- **需适配**：有价值，但依赖其他提交、涉及本地分叉逻辑或需要缩小移植范围。
- **已覆盖**：本地已有等价或更新实现，重复合入收益小。
- **不引入**：版本、赞助信息、废弃改动或当前无需求的功能。
- **待核实**：证据不足，不能给出可靠移植结论。

“已审”指静态检查提交差异及相关代码，不等于运行验证。后续实际移植时，记录本地落地提交及测试结果，保留原评审结论和变更原因。

## 单人自用筛选依据（2026-10-29 更新）

用户明确只关心服务安全、稳定性、正确性，以及 OpenAI 上游额度异常消耗。按主要使用 Codex / OpenAI Responses（HTTP、WS）筛选；是否使用图片、复合组、多 workspace、其他协议没有在本轮确认，相关建议保留条件，不假设这些功能已启用。

不直接开放公网能显著减少入站攻击面，但不足以证明服务安全：服务仍会处理上游内容、携带凭据访问外部服务，图片转存还会主动下载 URL。后者能通过服务访问本机/内网，属于 SSRF 风险，和谁能直接连接管理页面不是同一问题。参见 [OWASP SSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。本轮没有检查 ccvps 的实际监听、代理和访问控制配置。

### 先区分两种“计费”

- **OpenAI 上游实际消耗**：需要关注重复生成/重试、断线后继续执行、模型与 service tier/推理参数选择、工具调用、缓存复用及账号/workspace 归属。这些会改变发给上游的请求或执行次数，但当前没有证据证明哪项已导致异常消耗。
- **sub4api 本地记账**：分组倍率、价卡、退款、图片计价、用量统计主要改变本地余额、报表和额度门禁。它们不会直接修改 OpenAI 的计费规则或退回上游额度；如果依赖本地预算门禁限制使用，记账正确性仍有间接价值。

代码依据：`backend/internal/service/openai_gateway_usage.go:RecordUsage` 读取返回用量、计算本地倍率与费用；`gateway_usage_billing.go` 调用本地 `UsageBillingRepository.Apply` 结算。这和网关向上游发起生成请求是两条职责。014、015、111、202–205 不能仅因为涉及“计费”就升级为上游额度止损修复。

对你而言，这三项不是“重试越多越稳定”。验收要比较一次用户操作产生的上游尝试数，确认工具调用/内容输出后的请求不会被错误重放，以及取消、退避和总重试边界。离线 mock 能验证网关控制逻辑，不能证明 OpenAI 未计费。

本地还存在值得单独验收的断线路径：`detachUpstreamContext` 使用 `context.WithoutCancel`；账号 `cancel_upstream_on_client_disconnect` 默认 false；已有测试明确覆盖默认脱离客户端取消。**这不证明上游一定持续生成到结束**，因为后续读取、关闭连接和 WS 生命周期也会影响结果，但不能假设关闭 CLI 就立刻停止上游。本轮没有修改开关；不能为了节省额度直接全局改取消策略而丢失用量结算。后续需按 HTTP/WS 实际路径检查取消传播、排空边界与是否被客户端重新发起。

## 验收与边界

当前推荐顺序是：核心协议/并发小修复 → 已启用路径的安全与身份修复（命中高风险条件时提前）→ 针对实际失败的恢复改动。没有发现可仅凭静态差异就认定能解决“OpenAI 额度异常”的单个必选提交。

后续先用假上游完成 HTTP/WS 行为验收，重点记录上游尝试次数、取消传播、工具调用后是否重放、终态与 usage 是否保留、模型/推理参数和缓存身份是否被意外改写。保留本地已落地的 CLI 0.164 身份、UUID/缓存键策略、ctx_pool、BPS、强制用量队列、审计和价格门禁；除非证明有具体冲突，不顺手替换。

真实上游额度、缓存是否命中以及一次取消最终如何结算，仍需授权后的被动观测或账号侧证据；本轮不使用真实账号、不合入业务代码、不改部署。这里不承诺节省金额/额度，也不把本地账单当作官方账单。
